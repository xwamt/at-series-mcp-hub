# AT Series Hub Protocol v2 — progressive tool discovery

**Status:** Normative
**Date:** 2026-07-31
**Hub protocolVersion:** `2`
**Bridge wire protocolVersion:** `1` (unchanged; see [v1.md](./v1.md))
**Audience:** Hub implementers, MCP clients, and AT-family plugin authors

This document defines the Hub's progressive MCP tool exposure. It extends the Hub surface specified by Protocol v1; it does **not** change the Bridge registry or Bridge HTTP wire contract. A Bridge MUST continue to publish and serve `protocolVersion: 1`.

The design was accepted 2026-07-31.

## 1. Terms and compatibility

- **Business tool** is a current winning tool aggregated from healthy Bridges.
- **Full catalog** is all current winning business tools, including tools not presently returned by MCP `tools/list`.
- **Exposed tool** is a business tool currently returned by MCP `tools/list`.
- **Hub built-in** is one of the meta-tools in section 3.

Hub-reported `protocolVersion` values, including `at_list_providers` and `hub-version.json`, MUST be `2`. Bridge registry records and `GET /health` / `GET /tools` responses remain wire version `1`.

Progressive exposure changes only MCP `tools/list`. It MUST NOT change Bridge publication, the full catalog used by meta-tools, or the ability of the Hub to route a current winning business-tool name. Selection is therefore **not an ACL or authorization boundary**.

## 2. Discovery modes

The Hub resolves the mode from `AT_SERIES_TOOL_DISCOVERY`, unless its embedding runtime supplies an explicit mode. Valid values are:

| Value | Behavior |
|---|---|
| `auto` | Progressive exposure applies only when the full business-tool count is greater than the threshold. |
| `always` | Progressive exposure always applies. |
| `off` | All business tools are exposed; selection does not filter `tools/list`. |

Invalid or absent `AT_SERIES_TOOL_DISCOVERY` MUST resolve to `auto`.

`AT_SERIES_TOOL_DISCOVERY_THRESHOLD` controls the `auto` threshold. Its default is `20`. It MUST be a non-negative integer; invalid, empty, or absent values MUST resolve to `20`. In `auto` mode, exactly `20` business tools remain fully exposed; progressive exposure begins only above `20`.

When progressive exposure applies, MCP `tools/list` MUST return:

1. selected current business tools; and
2. every Hub built-in in section 3.

When it does not apply, it MUST return all current business tools and every Hub built-in. Hub built-ins are always exposed.

## 3. Hub built-ins and reservation

The following names are reserved Hub built-ins. A Bridge MUST NOT claim any of them in its published or live catalog:

| Name | Input | Result |
|---|---|---|
| `at_list_providers` | `{}` | The v1 `ListProvidersResult` object. |
| `at_search_tools` | `{ query: string, pluginId?: string, limit?: number }` | Array of `ToolSearchHit` objects. |
| `at_get_tool` | `{ name: string }` | Full `ToolCatalogEntry` plus `pluginId`. |
| `at_select_tools` | `{ pluginIds?: string[], names?: string[], mode?: "replace" \| "add" }` | Selection result in section 4. |
| `at_clear_tool_selection` | `{}` | `{ "selected": [] }`. |

All Hub built-ins have `risk: "read"` in the Hub catalog. A Hub MUST exclude any Bridge tool with a reserved name from aggregation and routing, even if that Bridge is otherwise healthy.

### 3.1 `at_list_providers`

`at_list_providers` has no input. Its result is the `ListProvidersResult` defined in [v1.md](./v1.md#85-built-in-tool-at_list_providers), including `hostApp`, `hubVersion`, `protocolVersion: 2`, provider/Bridge health, winning tool names, conflicts, and `ignoredUnscopedBridgeCount`. It MUST NOT expose Bridge tokens.

### 3.2 `at_search_tools`

`query` is required and MUST be a non-empty string. `pluginId`, when present, MUST be a non-empty string. `limit`, when present, MUST be a finite number. Invalid input returns:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "..." } }
```

Search is case-insensitive substring matching over each full-catalog tool's `name`, `title`, and `description`; `pluginId` restricts results to that provider. The default limit is `20`; the effective limit is clamped to the inclusive range `1..50`.

Each result is:

```json
{
  "name": "example_ping",
  "title": "Example Ping",
  "description": "Health ping for AT Example.",
  "risk": "read",
  "pluginId": "at.example"
}
```

### 3.3 `at_get_tool`

`name` is required and MUST be a non-empty string. It returns the full current winning `ToolCatalogEntry` and its `pluginId`:

```json
{
  "name": "example_ping",
  "title": "Example Ping",
  "description": "Health ping for AT Example.",
  "risk": "read",
  "inputSchema": { "type": "object", "properties": {} },
  "pluginId": "at.example"
}
```

An unknown name returns `{ "error": { "code": "NOT_FOUND", "message": "Unknown tool: <name>" } }`. Invalid input returns `VALIDATION_ERROR`.

## 4. Selecting first-class tools

`at_select_tools` takes one or both of:

- `pluginIds`: provider IDs. Every current winning business tool for each known provider is selected.
- `names`: current winning business-tool names to select.

At least one non-empty `pluginIds` or `names` array is required. Every supplied array element MUST be a non-empty string. `mode` MUST be `replace` or `add` when supplied; its default is `replace`.

- `replace` clears the prior selection, then selects every known requested provider/tool.
- `add` retains the prior selection, then adds every known requested provider/tool.
- Unknown provider IDs and unknown names do not fail the request. They are reported in the result and select nothing.
- If a `replace` request contains only unknown values, the resulting selection is empty.

The result is:

```json
{
  "selected": ["example_ping"],
  "unknownNames": ["missing_tool"],
  "unknownPluginIds": ["at.missing"],
  "exposedBusinessToolCount": 1,
  "mode": "replace"
}
```

`selected` contains current selected winning tool names. `exposedBusinessToolCount` is the number of business tools currently exposed after applying the active discovery mode; in `off` mode, or in `auto` mode at or below the threshold, it can exceed `selected.length`.

Selection is Hub-process state. On catalog refresh, selections for names that are no longer current winners MUST be discarded. Calling `at_clear_tool_selection` clears that state; it does not change the catalog or a Bridge.

MCP clients SHOULD use the following flow when progressive exposure applies:

1. Call `at_list_providers` to identify providers.
2. Call `at_search_tools` and, as needed, `at_get_tool` against the full catalog.
3. Call `at_select_tools`.
4. On `notifications/tools/list_changed`, refresh `tools/list` and call selected business tools as first-class MCP tools.

## 5. `tools/list_changed`

The Hub advertises MCP tools list-change support. After its initial catalog baseline, it MUST emit `notifications/tools/list_changed` when the set of exposed tool names changes.

This includes selection or clear operations that change exposed names, and registry/health/catalog changes that change exposed names. It does not require a notification when only non-name metadata changes, or when a full-catalog change does not alter the currently exposed name set.

## 6. Migration from v1

Existing Bridge and plugin integrations require no code changes for this Hub v2a exposure behavior:

- Continue publishing the complete Bridge `GET /tools` catalog and registry `tools` snapshot with `protocolVersion: 1`.
- Do not filter a Bridge catalog based on Hub selections.
- Continue using the v1 Bridge HTTP endpoints and token contract.

The Hub's `at_list_providers` and `hub-version.json` stamps move to `protocolVersion: 2`. Clients that need the v1 all-tools `tools/list` behavior can set:

```text
AT_SERIES_TOOL_DISCOVERY=off
```

This is the compatibility escape hatch. It preserves full business-tool exposure while leaving all Hub built-ins available.
