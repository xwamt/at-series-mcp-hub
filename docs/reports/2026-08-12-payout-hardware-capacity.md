## 1. 结论

**当前硬件资源足够。** 在真实订单突发分钟内，应用主机 CPU / load、Aurora QPS / threads_running 与无单日同钟点几乎无差；唯一可见的高峰增量是 **连接数**，且相对 `max_connections=4000` 仍极低。

**瓶颈不在硬件饱和，而在订单落库吞吐形态**：`create_time` 粒度上峰值约 **50 笔/分钟**（约 0.8–1 笔/秒串行感），瞬时「几百笔涌入」更可能发生在入口/队列，入库被摊平到数分钟。

**理论可接受量（硬件视角，保守）：**

| 口径 | 已观测峰值 | 硬件仍充裕的理论上限（估） | 说明 |
| --- | ---: | ---: | --- |
| 单分钟入库 | ~50 笔/min | **≥ 500–1,000 笔/min** | CPU/QPS 几乎无增量，按连接头寸与 10–20× 安全余量外推 |
| 3 分钟突发簇 | ~98 笔 / 3min | **≥ 1,000–2,000 笔 / 3min** | 同上；需应用并发与通道侧先顶住 |
| 30 分钟高峰簇 | 605 笔 / 30min | **≥ 6,000–10,000 笔 / 30min** | 硬件仍非首限；先验证队列积压与渠道超时 |
| 工作日日量 | ~3,000–3,500 | **≥ 15,000–25,000 / 日** | 若仍是分批突发而非全日匀速 |

> 以上是 **主机/MySQL 硬件** 外推，不是支付通道/业务确认/幂等锁的上限。若入口瞬间丢入数百笔，应用层排队变长，体感「卡住」仍可能发生，即使 CPU 仍很低。

## 2. 方法（为何不用小时均值）

1. 从订单表找 **分钟桶** 峰值，不以小时平均摊薄。
2. 取最忙 3 分钟窗（02:41–02:44）用 Prometheus `rate(...[30s])`、`step=15s` 看瞬时尖峰。
3. 对照 **无订单日（08-09）同钟点**，算高峰 − 基线增量。
4. Loki 在同一 3 分钟窗扫 `ERROR` / timeout / exception（payment / openapi / taskcenter）。

## 5. 容量外推逻辑

1. **CPU / QPS / load / threads_running**：高峰相对无单增量 ≈ 0 → 无法用「Δ资源 / 余量」做紧贴外推；说明当前突发远未碰到硬件墙。
2. **连接数**：Δ≈+25 primary（相对无单）。距 4000 上限余量 >98%。即使线性放大 20×（~500 连接），仍仅约 12.5% 上限——且真实池化未必线性。
3. **内存**：高水位是常驻态，不是突发尖峰；扩容决策应看 JVM heap/GC，而不是「订单多了内存就涨」。
4. **实际吞吐上限候选**（需另开专题，非本次硬件结论）：
   - 入库串行/锁竞争（~50/min 形状）
   - MQ/线程池队列深度
   - 支付通道 QPS / 确认链路

因此硬件结论写成：**现阶段再涨一个数量级的分钟突发，主机与 Aurora 仍大概率够用；先盯应用队列与通道，而不是加机器。**

---

## 6. 建议

1. 监控告警用 **1m/30s** 峰值，不要用 1h 平均判断代发压力。
2. 对 payment-engine 补 **队列深度 / 处理延迟 / 线程池拒绝** 指标，才能量化「瞬间几百单」入口侧。
3. 内存 ~87% 建议查 JVM `-Xmx` 与 RSS，属常驻配置问题，与本月订单增量解耦。
4. 若要验证理论上限，做一次受控压测：按 200 / 500 / 1000 笔/min 灌入，观察连接、队列、渠道超时，而不是只看 CPU。
